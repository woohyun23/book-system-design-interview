# 1장 질문 및 답변

## 현업에서 캐시 만료 시간을 설정할 때 고려할 사항

### 1. 데이터의 허용 가능한 오래됨을 정한다

> TTL ≤ 서비스가 허용하는 데이터 지연 시간

#### 설정 예시

| 데이터 | 초기 TTL 예시 | 이유 |
| --- | --- | --- |
| 실시간 주가 | 수 초 이하 또는 이벤트 기반 갱신 | 최신성이 매우 중요 |
| 인기 게시글 목록 | 10초~1분 | 약간의 지연 허용 |
| 상품 상세 정보 | 1~10분 | 변경 빈도가 비교적 낮음 |
| 존재하지 않는 데이터 | 5~30초 | 반복적인 잘못된 조회 방지 |
| 해시가 붙은 CSS·JS | 수개월~1년 | 내용 변경 시 URL도 변경 |
| 사용자 세션 | 인증 정책에 맞춰 설정 | 보안 및 로그인 유지 시간과 연결 |

### 2. 변경 빈도보다 허용 가능한 불일치가 중요하다

데이터가 한 시간에 한 번 변경된다고 해서 반드시 TTL을 한 시간으로 정하는 것은 아닙니다.

- 변경 즉시 반영되어야 한다면 TTL을 짧게 설정하거나 변경 시 캐시를 삭제합니다.
- 5분 정도 오래된 값도 괜찮다면 TTL을 5분 전후로 설정할 수 있습니다.
- 변경 이벤트로 캐시를 정확히 삭제하더라도 TTL을 안전장치로 함께 둘 수 있습니다.

Redis 공식 예제도 프로덕션에서는 데이터의 **staleness tolerance**, 즉 오래된 값을 허용할 수 있는 시간에 맞춰 TTL을 선택하라고 안내합니다.

- [Redis Cache-Aside 가이드](https://redis.io/docs/latest/develop/use-cases/cache-aside/php/)

### 3. 동일한 TTL에 약간의 무작위 값을 추가한다

상품 캐시 10만 개에 모두 정확히 10분을 설정하면 10분 후 동시에 만료될 수 있습니다. 그러면 요청이 한꺼번에 원본 DB로 몰리는 Cache Avalanche 현상이 발생합니다.

```text
기본 TTL: 600초
실제 TTL: 540~660초 사이의 임의 값
```

AWS도 캐시 키의 동시 만료를 분산하기 위해 TTL에 Jitter를 추가하는 방식을 권장합니다.

```text
실제 TTL = 기준 TTL + 무작위로 생성한 Jitter
```

> **Jitter**: 동일한 시점에 몰리는 작업을 분산하기 위해 기준 시간에 추가하는 무작위 시간

- [AWS Redis 캐싱 전략](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/database-caching-strategies-using-redis.pdf)

### 4. 처음 정한 TTL을 기준으로 운영 지표를 활용해 조정한다

다음 지표를 확인합니다.

- 캐시 적중률
- DB 요청량과 부하
- 캐시 만료 후 응답 지연
- TTL로 만료된 키의 수
- 메모리 부족으로 제거된 키의 수
- 오래된 데이터로 발생한 오류나 사용자 불편

판단은 다음과 같이 할 수 있습니다.

```text
TTL이 너무 짧음
→ 캐시 미스와 DB 요청 증가
→ TTL 증가 검토

TTL이 너무 긺
→ 오래된 데이터 노출 증가
→ TTL 단축 또는 변경 이벤트 기반 무효화 검토

evicted_keys가 많음
→ TTL보다 메모리 용량이나 Eviction 정책 점검
```

## 트래픽을 분산시켜 주는 로드밸런서가 죽으면 서비스가 어떻게 동작하는가?

로드밸런서는 사용자와 여러 애플리케이션 서버 사이의 입구 역할을 합니다.

서버 A 한 대가 죽으면 로드밸런서가 헬스 체크를 통해 이를 감지하고 서버 B와 C로 요청을 보낼 수 있습니다. 하지만 로드밸런서가 한 대뿐이고 그 로드밸런서 자체가 죽는다면, 정상적인 애플리케이션 서버가 남아 있어도 사용자는 서버에 접근하기 어려워집니다.

즉, 단일 로드밸런서는 새로운 **SPOF(Single Point of Failure, 단일 장애 지점)**가 됩니다.

로드밸런서 장애가 발생하면 일반적으로 다음과 같은 현상이 발생합니다.

- 로드밸런서를 통과하던 기존 연결이 끊길 수 있습니다.
- 새로운 요청은 연결 실패나 타임아웃을 경험합니다.
- 애플리케이션 서버가 정상이어도 외부에서는 서비스에 접근하지 못합니다.
- 장애 조치 과정에서 일부 요청이 실패하거나 재시도될 수 있습니다.

이러한 문제를 예방하기 위해 로드밸런서도 이중화합니다.

- **Active-Standby 방식**: Active 로드밸런서가 죽으면 Standby가 가상 IP를 넘겨받습니다.
- **Active-Active 방식**: 여러 로드밸런서가 동시에 트래픽을 처리합니다.

## 왜 서비스 규모 확장 시 서비스 간의 결합을 느슨하게 해야 하는가?

결합이 강하다는 것은 한 서비스의 변경이나 장애가 다른 서비스에 직접적인 영향을 준다는 뜻입니다.

서비스 간 결합을 느슨하게 함으로써 다음과 같은 장점을 얻을 수 있습니다.

- 장애 범위를 줄일 수 있습니다.
- 필요한 서비스만 독립적으로 확장할 수 있습니다.
- 독립적으로 변경하고 배포할 수 있습니다.
- 트래픽 급증을 흡수할 수 있습니다.

다만 느슨한 결합이 무조건 비동기 메시징을 의미하는 것은 아닙니다.

- 즉시 결과가 필요한 조회나 결제 승인은 동기 API가 적절할 수 있습니다.
- 후속 알림, 통계 집계, 로그 처리 등은 비동기 이벤트가 적절할 수 있습니다.
- 동기 호출에는 타임아웃, 서킷 브레이커, 제한적인 재시도가 필요합니다.
- 비동기 처리에는 중복 메시지, 순서, 재처리, 최종적 일관성을 다뤄야 합니다.

> 느슨한 결합의 목적은 무조건 서비스를 잘게 나누는 것이 아니라, 한 서비스의 변경·트래픽·장애가 전체 시스템으로 전파되지 않도록 경계를 만드는 것입니다.

## 샤딩 키를 정할 때 실제로 어떤 데이터를 기준으로 삼아야 고르게 분할할 수 있는가?

좋은 샤딩 키는 단순히 데이터의 개수만 고르게 나누는 키가 아닙니다.

- 저장되는 데이터의 양이 고르게 분산되어야 합니다.
- 읽기와 쓰기 트래픽도 고르게 분산되어야 합니다.
- 자주 실행하는 조회가 가능한 한 적은 샤드를 방문해야 합니다.

MongoDB에서도 좋은 샤딩 키의 조건으로 다음 항목을 제시합니다.

- **Cardinality(다양성)**: 서로 다른 키 값이 충분히 많아야 합니다.
- **Frequency(등장 빈도)**: 특정 값에 데이터와 요청이 몰리지 않아야 합니다.
- **Monotonicity(단조 증가 여부)**: 계속 증가하는 값으로 인해 쓰기가 한 샤드에 집중되지 않아야 합니다.
- **Query Pattern(조회 패턴)**: 자주 실행하는 조회가 여러 샤드에 불필요하게 퍼지지 않아야 합니다.

## 시스템을 단일 서버에서 시작해 샤딩을 가장 나중에 적용하는 이유가 있을까?

이 순서는 절대적인 규칙이 아니라, 현재 발생한 병목을 가장 단순하고 비용이 적은 방법부터 해결하는 일반적인 흐름입니다.

초기 서비스는 데이터 규모와 실제 트래픽 패턴을 정확히 알기 어렵습니다. 이때 처음부터 샤딩을 적용하면 아직 존재하지 않는 문제를 해결하기 위해 불필요한 복잡성을 미리 부담하게 됩니다.

즉, **오버 엔지니어링 가능성이 높아집니다.**

일반적으로 다음과 같이 관측된 병목에 맞춰 점진적으로 확장합니다.

```text
단일 서버
  ↓
웹 서버와 데이터베이스 분리
  ↓
로드밸런서와 웹 서버 수평 확장
  ↓
데이터베이스 복제
  ↓
캐시와 CDN 도입
  ↓
단일 데이터베이스의 저장 용량 또는 쓰기 처리량 한계 도달
  ↓
샤딩 도입
```

CDN은 정적 콘텐츠가 많거나 여러 지역의 사용자가 존재한다면 초기부터 도입해도 괜찮습니다. 샤딩 역시 초기부터 대규모 데이터가 발생할 것이 확실하거나 테넌트·국가별 데이터 분리 요구사항이 명확하다면 일찍 적용할 수 있습니다.

따라서 확장 기술의 도입 순서를 그대로 따르기보다 현재 병목과 요구사항에 가장 적은 복잡성으로 대응해야 합니다.

## 로드밸런서는 트래픽을 어떤 기준으로 분산시킬까?

로드밸런서는 먼저 헬스 체크에 통과한 서버만 대상으로 삼고, 설정된 알고리즘에 따라 요청을 분배합니다.

- **라운드 로빈**: 요청을 서버에 순서대로 전달합니다. 서버 성능과 요청 처리 시간이 비슷할 때 단순하고 효과적입니다.
- **가중 라운드 로빈**: 성능이 좋은 서버에 더 많은 요청을 전송합니다.
- **최소 연결 수**: 현재 활성 연결이 가장 적은 서버에 요청을 전송합니다.
- **최소 미처리 요청 또는 최소 응답 시간**: 진행 중인 요청이 적거나 최근 응답 시간이 빠른 서버에 요청을 전송합니다.
- **IP 해시 또는 일관된 해시**: 클라이언트 IP, 세션 ID, 사용자 ID, 요청 URI 등을 해시하여 같은 값의 요청을 같은 서버로 전송합니다.
- **요청 내용에 따른 라우팅**: 7계층 로드밸런서는 요청의 경로, 호스트, 헤더 등을 확인하여 대상 서비스 그룹을 먼저 선택할 수 있습니다.

## 캐시 메모리 과할당 문제가 발생하지 않을까? 해결책은 무엇일까?

캐시에 계속 데이터를 추가하면서 제한을 두지 않으면 메모리가 부족해져 Redis 프로세스가 종료되거나 운영체제의 OOM Killer에 의해 제거될 수 있습니다.

> **OOM Killer**: 리눅스 운영체제가 메모리 부족으로 시스템 전체가 멈추는 것을 방지하기 위해 특정 프로세스를 강제로 종료하는 기능

Redis에서는 일반적으로 `maxmemory`로 데이터에 사용할 메모리 한도를 정하고, 한도에 도달했을 때 `maxmemory-policy`에 따라 키를 제거하거나 새로운 쓰기를 거절합니다.

### 1. 메모리 사용 한도를 설정한다

`maxmemory`를 설정하고 실제 RAM보다 낮게 지정하여 운영체제, 복제 버퍼, AOF·RDB 작업 등에 필요한 여유 공간을 남겨야 합니다.

### 2. 용도에 맞는 제거 정책을 선택한다

| 정책 | 동작 | 적합한 경우 |
| --- | --- | --- |
| `allkeys-lru` | 가장 오래 사용되지 않은 키 제거 | 일반적인 조회 캐시 |
| `allkeys-lfu` | 사용 빈도가 낮은 키 제거 | 일부 인기 데이터가 반복 조회되는 경우 |
| `volatile-ttl` | 만료 시간이 가장 가까운 키 제거 | TTL이 설정된 키만 제거하려는 경우 |
| `noeviction` | 키를 제거하지 않고 새로운 쓰기에 오류 반환 | 캐시가 아닌 중요한 상태 저장소 |

세션, 분산 락, 메시지처럼 사라지면 안 되는 데이터와 캐시 데이터를 동일한 Redis에 섞어 두면 제거 정책을 결정하기 어려워집니다. 가능하면 용도별 Redis 인스턴스 또는 클러스터를 분리하는 것이 안전합니다.

### 3. 모든 캐시 데이터에 적절한 TTL을 둔다

한 번에 많은 키가 만료되면 원본 DB에 트래픽이 몰릴 수 있습니다. TTL에 Jitter를 적용해 만료 시점이 분산되도록 합니다.

### 4. 큰 키와 불필요한 데이터를 줄인다

- 지나치게 큰 문자열이나 컬렉션을 저장하지 않습니다.
- 전체 객체 대신 필요한 필드만 캐싱합니다.
- 긴 키 이름과 중복 데이터를 최소화합니다.
- 큰 컬렉션을 여러 키로 분할합니다.
- 직렬화 방식과 압축 효과를 확인합니다.
- 캐싱 효과가 낮은 일회성 데이터는 저장하지 않습니다.

### 5. 메모리 지표를 모니터링한다

| 지표 | 의미 |
| --- | --- |
| `used_memory` | Redis가 할당한 메모리 |
| `used_memory_rss` | 운영체제가 Redis 프로세스에 실제로 할당한 메모리 |
| `mem_fragmentation_ratio` | 메모리 단편화 정도 |
| `evicted_keys` | 메모리 부족으로 제거된 키의 수 |
| `expired_keys` | TTL로 만료된 키의 수 |
| Cache Hit/Miss Rate | 캐시 적중률과 미스율 |

### 6. 캐시 제거 후 DB 과부하에도 대비한다

메모리 부족으로 많은 키가 제거되면 캐시 미스가 급증하여 DB로 요청이 몰릴 수 있습니다. 다음 방법을 함께 적용합니다.

- **Request Coalescing**: 동일한 키에 대한 동시 조회를 하나의 DB 요청으로 합칩니다.
- TTL Jitter를 적용합니다.
- 자주 조회되는 데이터를 미리 적재합니다.
- 오래된 값을 잠시 제공하면서 백그라운드에서 캐시를 갱신합니다.
- DB 요청 속도 제한과 백프레셔를 적용합니다.
- Redis Cluster를 통해 수평 확장합니다.
- 실제 캐시 효율이 낮은 데이터를 제거합니다.

> **백프레셔(Backpressure)**: 요청을 받는 쪽의 처리 속도보다 요청이 더 빠르게 들어올 때, 보내는 쪽의 속도를 제한하거나 요청을 잠시 대기시키는 제어 방식
