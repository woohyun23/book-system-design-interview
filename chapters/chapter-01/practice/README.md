## 데이터베이스

### 관계형 데이터베이스 (RDBMS)

: 자료를 테이블과 행과 열로 표현

- SQL을 사용해 여러 테이블의 데이터를 조인하여 조회 가능
- MySQL, 오라클 데이터베이스, PostgreSQL 등

### 비 관계형 데이터베이스 (NOSQL)

- 사용하기 적합한 경우
    - 아주 낮은 응답 지연시간 요구
    - 비정형 데이터 사용
    - 데이터 직렬화/역직렬화만 가능 ()
    - 아주 많은 양의 데이터 저장 필요
- 주요 유형
    - Key-Value Store
        - 키를 이용해 값을 저장하고 조회
        - Redis, Amazon DyanmoDB
    - Document Store
        - JSON과 유사한 문서 단위로 데이터로 저장
        - MongoDB, CouchDB
    - Column Store
        - 행마다 서로 다른 열을 가질 수 있으며 대규모 분산 처리에 적합
        - Cassandra, HBase
    - Graph Store
        - 노드와 간선으로 데이터 간의 관계를 표현
        - Neo4j

## 규모 확장

### 수직적 규모 확장 (scale up/ vertical scaling)

- 서버에 고사양 자원(고사양 CPU/RAM) 추가
- 서버에 유입되는 트래픽의 양이 적은 경우에 적합
- 단점
    - 한계 존재 (사양의 업그레이드에 한계 존재)
    - 장애에 대한 자동복구 방안, 다중화 방안 제시 X
      → 서버에 장애 발생 시, 서버 중단

### 수평적 규모 확장 (scale out)

- 서버 추가
- 대규모 애플리케이션에 적합

### 로드 밸런서

- 웹 서버들에게 트래픽 부하를 고르게 분산하는 역할
- 부하 분산 집합에 웹 서버를 추가하면 장애를 자동 복구하지 못하는 문제 해결
  웹 계층의 가용성 향상

### 데이터베이스 다중화

- Master-Slave 관계 설정
    - Master
        - 데이터 원본 저장
        - 쓰기 연산 지원
    - Slave
        - 사본 저장
        - 일반적으로 읽기 연산만 지원
          → 대부분의 서비스에서 읽기 연산의 비중이 높기 때문에 통상적으로 Slave DB의 수가 더 많음
- 장점
    - 더 나은 성능 - 읽기 연산을 지원하는 DB가 증가하면서 병렬 처리 가능한 Query 수 증가
    - 안정성 - 일부 DB에 문제가 생겨도 다른 DB에서 데이터에서 읽기 연산이 가능하므로 데이터 보존가능
    - 가용성 - 데이터를 여러 지역에 복제해 둠으로써, 하나의 데이터베이스 서버에 장애가 발생하더라도 다른 서버의 데이터를 가져와 서비스 지속 가능

## 캐시

- 사용 시 유의할 점
    - 캐시는 어떤 상황에 바람직한가?

      데이터 갱신은 자주 일어나지 않지만, 참조는 빈번하게 일어나는 경우 고려할만 한 상황이다.

    - 어떤 데이터를 캐시에 두어야 하는가?

      캐시는 데이터를 휘발성 메모리에 두므로, 영속적으로 보관할 데이터를 캐시에 두는 것은 바람직하지 않다.

    - 캐시에 보관된 데이터는 어떻게 만료되는가?

      정책 마련 필요, 만료된 데이터는 캐시에서 삭제되어야 한다.
      만료 정책이 없으면 데이터는 캐시에 계속 남게 된다.
      만료 기한이 너무 짧으면 DB를 자주 읽게 되어 무의미해지고,
      만료기한이 너무 길면 원본과 차이 날 가능성이 높아진다.

    - 일관성은 어떻게 유지되는가?

      저장소의 원본을 갱신하는 연산과 캐시를 갱신하는 연산이 단일 트랜잭션으로 처리

    - 장애에는 어떻게 대처할 것인가?

      캐시 서버를 한 대만 두는 경우, 해당 서버는 단일 장애 지점(SPOF)이 되어버릴 가능성 존재
      SPOF를 피하기 위해 열러 지역에 걸쳐 캐시 서버 분산


## CDN

- 정적 컨텐츠 전송에 주로 사용하는, 지리적으로 분산된 서버의 네트워크
  → 요청 경로, 질의 문자열, 쿠키, 요청 헤더 등의 정보에 기반하여 HTML 페이지 캐싱
- 이미지, 비디오, CSS, JS 파일 등을 캐시 가능
- CDN 사용시 고려사항
    - 비용
    - 적절한 만료 시한 설정
    - CDN 장애에 대한 대처 방안
    - 컨텐츠 무효화 방법 - 만료되지 않은 컨텐츠를 CDN에서 제거
        - CDN 서비스 사업자가 제공하는 API 사용
        - 컨텐츠가 변경되면 새로운 URL을 사용하므로, 기존 CDN 캐시 만료를 기다리지 않고
          새 컨텐츠의 제공이 가능한 Object Versioning 사용

## 무상태 웹 계층

- 웹 계층에서 상태 정보 (사용자 세션 데이터와 같은)의 제거 필요
    - 상태 정보를 지속성 저장소에 보관하고, 필요할 때 가져와 사용

### 상태 정보 의존적인 아키텍처

- 상태(클라이언트 정보)를 유지하여 요청들 사이에 공유
- 같은 클라이언트로부터의 요청은 항상 같은 서버로 전송
    - 고정 세션 기능 제공하지만, 이는 로드밸런서에 부담 + 서버 장애 처리 복잡

### 무상태 아키텍처

- 사용자로부터의 HTTP 요청이 어떤 웹 서버로도 전달 가능
- 웹 서버에서 상태 정보가 필요한 경우
  → 공유 저장소로부터 데이터를 가져와 사용

## 데이터베이스의 규모 확장

### 수직적 확장 (scale up)

- 약점
    - 수직적 확장에는 한계 존재
    - SPOF로 인한 위험성 높음
    - 고비용

### 수평적 확장 (sharding)

- 대규모 DB를 샤드 단위로 분할하는 기술
- 모든 샤드는 같은 스키마를 사용하지만, 샤드에 보관되는 데이터에는 중복 X
- 샤딩 키 지정
    - 데이터가 어떻게 분산될지 정하는 하나 이상의 칼럼으로 구성
- 도입 시, 발생 가능한 문제 상황
    - 데이터의 재 샤딩
        - 데이터가 너무 많아져 하나의 샤드로 감당하기 어려운 경우
        - 샤드간 데이터 분포가 균등하지 못한 경우
    - 유명인사 문제
        - 특정 샤드에 질의가 집중되어 서버에 과부하가 발생하는 경우
    - 조인과 비정규화
        - 여러 샤드에 걸친 데이터 조인이 어려워져 데이터베이스를 비정규화하여 하나의 테이블에서 질의가 수행될 수 있게 재구성
